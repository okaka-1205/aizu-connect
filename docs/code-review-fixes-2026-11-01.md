## 変更

| 問題 | 対応 |
| --- | --- |
| 削除中の新規申請が清掃から漏れる | 清掃開始前にユーザー・イベントを削除中へ変更し、サーバー専用の`deletionLocks`を保存する。申請、企画保存、投稿編集などは現在のユーザー・イベントをトランザクション内で確認する。関連する直接クライアント書き込みも削除記録で拒否する。 |
| 削除後に通知・活動実績が再作成される | 現在のユーザー、主催者、イベント、申請を確認し、副作用と同じトランザクションで整合させる。現在の申請状態と異なる古い状態通知や、中止イベントの新規活動実績を作らない。既存実績は再試行で作成時刻を変更しない。 |
| CSVの数式対策不足 | 文字列の先頭が数式記号・全角記号・対象制御文字となる場合、引用したセル内にタブを付けて文字列として出力する。通常文字列、引用符、改行、数値の出力は維持する。 |
| 中止イベントの出席登録 | Rulesと画面で公開中のイベントに限定する。開催3時間前からという既存条件は維持し、手動出欠に新しい終了期限は加えない。既に発行済みの実績は中止後も削除しない。 |
| 他人の保存先IDの先取り | `savedEvents`の作成時に、IDが本人UIDとイベントIDから作る正規のIDと一致することを検証する。既存の他人のデータへの読み取り・更新・削除は引き続き拒否する。 |
| 学生主催者が活動報告を公開できない | FirestoreとStorageの両方で学生・団体のイベント所有者を許可する。所有者確認、サイズ、スキーマ、権利確認は維持する。報告公開時の失敗も画面へ通知する。 |
| 公開停止後の件数表示の不一致 | `syncEventPublicProfile`を追加。公開・公開停止・再審査・中止・削除などで、現在の公開イベントから件数とプロフィール情報を再集計する。順序が逆のトリガーや重複実行でも差分を重ねず、現在値へ収束させる。 |

公開件数は、トランザクション内の集計クエリと最新公開イベントの取得を使用する。主催者の全イベント本文をブラウザーやFunctionsへ列挙する方式ではない。使用するインデックスは既存の`createdBy`・`status`・`startAt`。集計クエリのトランザクション対応は[公式のTransaction API](https://docs.cloud.google.com/nodejs/docs/reference/firestore/latest/firestore/transaction#get_aggregatequery)と、現在インストールされたSDKの型定義で確認した。

## 修正中に追加で見つけて対応した点

- 遅れたイベント作成トリガーが、削除したチャットや受付コードを再作成できる経路があった。作成トランザクションでも現在のイベント・主催者を確認する。
- キャンセル直後の退会では、申請のキャンセルトリガーが未処理のまま、退会側が申請を削除する組み合わせがある。新しい`capacityHeld`と処理済みの`capacityReleased`で予約枠を管理し、退会側でも未処理分を一度だけ精算する。旧データは既存の処理済み記録と待機番号を確認し、再減算を避ける。
- 同じ対象への異なる削除リクエストが並行することを防ぐため、対象単位の実行リースを設けた。通常の失敗は再試行可能な状態とし、実行が中断した場合は15分のリース満了後に再試行できる。Functionsの実行上限は9分。
- チャットのメンバー削除と人数変更を同じトランザクションにまとめた。イベント削除では、その部屋のミュート設定も清掃する。削除済みイベントへのアンケート・設定、削除済み主催者への保存などの作り直しも防ぐ。

削除記録には識別子と処理状態だけを残す。削除済みIDの再作成を防ぐ目的であり、氏名やメッセージ本文は保存しない。クライアントは記録を直接読み書きできない。管理画面には「削除処理中」を追加し、途中失敗した削除を再試行できるようにした。削除中のアカウント復旧・イベント再公開は許可しない。

## 本番反映時の対象と限界

- Hosting、Functions、Firestore Rules、Storage Rulesが反映対象。新しい`syncEventPublicProfile`も必要になる。インデックス定義の追加はない。
- 既に不正なIDで保存されたブックマーク、古い公開件数、過去の人数不整合が本番にあるかは今回調べていない。ルール修正だけで既存の不正な保存先を直したり、未更新プロフィールの件数を全件補正したりはしない。反映時に有無を読み取り確認し、必要な整理・再集計を行う。
- CSVについては、実際の出力処理を通した生成内容をテストした。Excelなどの実機での実行試験は行っていない。CSVは対象ソフト・保存後の再オープンによって挙動が異なるため、全表計算ソフトへの安全性を保証する結果ではない。[OWASP解説](https://owasp.org/www-community/attacks/CSV_Injection)
- 本番へのデプロイ、データ修復、Auth設定の変更は行っていない。
