## 再現した問題

### 1. P1：確認した版と異なるイベント内容を公開できる

参照：`functions/src/callables/adminManageResource.ts:730`、`:757`、`:775`、`functions/src/index.ts:140`、`src/screens/admin/hooks/useAdminActions.ts:110`。

承認処理はイベントを取得し、`pending_review`と必要な表示を確認してから、別の書き込みで`published`に更新する。主催者の編集はトランザクションで行われるが、承認の読み取りと書き込みの間に編集が完了すると、新しい本文に古い確認結果を適用できる。承認リクエストにも、管理者が確認した内容の版がない。

再現では、管理者が`Reviewed version`を取得した直後、主催者が正規の`saveEventPlan`で`Changed after admin check`へ変更し、その内容が再確認なしで`published`になった。

対応：画面で確認したrevisionまたは更新時刻を承認要求に含め、トランザクション内で現在の版・状態と一致する場合だけ承認する。版が違えば再確認を求める。単にトランザクションを自動再試行して新しい版を承認する対応では、確認した内容との一致を保証できない。

### 2. P1：退会削除の再試行で人数が二重に減り、定員超過につながる

参照：`functions/src/callables/adminManageResource.ts:354`、`:361`、`:371`。

参加人数を減らすトランザクションと申込の削除が別の処理になっている。人数の減算後に申込削除が失敗すると、再試行時に同じ申込を再取得してもう一度減算する。同じ管理操作のリクエストIDを使用しても、この途中段階は保護されない。

再現では、定員2・人数2から1人を退会させ、申込削除だけを1回失敗させた。人数は最初に1、再試行後に0になったが、他の1人の申込は残っていた。その後の正規の申込処理で2人を追加すると、定員2に対して有効な申込が3件になった。

対応：申込の処理済み状態または削除と人数の変更を同じトランザクションに含め、再実行で減算しないようにする。残りの関連データの削除は、再試行可能な段階に分ける。

### 3. P2：イベント公開後の失敗から、監査記録を復旧できない

参照：`functions/src/callables/adminManageResource.ts:775`、`:805`、`:816`、`:866`。

イベントの公開、監査ログ、管理操作の完了記録が別々に書き込まれる。公開後に監査ログの保存が失敗すると、イベントは公開済みのまま操作は失敗になる。再試行しても、すでに`pending_review`ではないため監査ログの保存まで進めない。

再現では、監査ログの書き込みを1回だけ失敗させた。イベントは`published`、同じ要求の再試行は`failed-precondition`、監査ログは存在しない状態になった。

対応：本体の状態変更・監査ログ・操作の完了記録を原子的に保存する。通知などの外部処理は、その後に冪等に実行できる形にする。

### 4. P2：未来の投稿時刻を指定して、新着メッセージを見えにくくできる

参照：`firestore.rules:679`、`src/repositories/chatRepository.ts:233`。

メッセージの作成時刻は`timestamp`であることだけを検証しており、サーバー時刻との一致を求めていない。一方、通常の履歴取得は時刻順の末尾100件なので、参加メンバーが未来の日付の投稿を作成すると、その後の正常な投稿より常に後ろに並ぶ。

再現では、正規のメンバー権限で2099年の投稿100件を書き込めた。その後にサーバー時刻で投稿したメッセージは、通常の末尾100件に含まれなかった。過去の履歴の追加取得で到達はできるが、新着表示を妨害できる。

対応：投稿の`createdAt`を`request.time`に一致させる。既存クライアントは`serverTimestamp()`を使用している。同様に、部屋の最終投稿時刻や既読時刻の信頼境界も揃える。

### 5. P2：閲覧専用チャットでも本文を編集できる

参照：`functions/src/index.ts:603`、`:626`、`src/screens/shared/MessagesTab.tsx:369`。

新規投稿は部屋が`active`であることをRulesが確認するが、メッセージ編集APIはメンバーと投稿者の一致だけを確認し、部屋の状態を確認しない。中止後に`read_only`となった部屋でも、自分の既存投稿の本文を書き換えられる。

再現では、新規投稿はRulesに拒否された一方、同じ部屋の既存投稿の編集は成功した。

対応：編集APIにも部屋の状態の検証を加え、画面の編集操作と揃える。削除の可否は、閲覧専用化の目的と本人の削除操作を踏まえて別途明示する。

### 6. P2：削除した本文がチャット一覧に残る

参照：`functions/src/index.ts:650`、`src/repositories/chatRepository.ts:53`、`src/screens/shared/messages/ConversationList.tsx:120`。

削除時にはメッセージ本体を削除済み文言に置き換えるが、部屋に保存された`lastMessageText`を更新しない。この値はチャット一覧と一覧検索に使用されるため、最新投稿を削除しても元の本文が一覧に残る。編集でも同様にプレビューとの不一致が起きる。

再現では、メッセージ本体は削除済みになったが、部屋の一覧プレビューは元の本文のままだった。

対応：プレビュー元のメッセージIDを保持し、編集・削除対象が最後の投稿である場合にプレビューも更新する。同時に届いた別の新着投稿を古い値で上書きしないよう、トランザクションで整合させる。
