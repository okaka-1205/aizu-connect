## 1. P2：他人の保存先IDを先取りし、イベントの保存を妨げられる

参照：

- [保存ドキュメントの作成ルール](/Users/okk/my-project/aizu-connect/firestore.rules:780)
- [画面が使用する保存先ID](/Users/okk/my-project/aizu-connect/src/App.tsx:1439)

画面はイベントを保存するとき、`savedEvents/{本人UID}_{イベントID}`へ書き込む。一方、Rulesは作成時のデータ内の`userId`が本人かだけを確認し、ドキュメントIDと本人UID・イベントIDの対応を確認しない。

このため、有効な学生アカウントが、他人の保存先パスへ自分を所有者とするドキュメントを先に作成できる。その後、本来の利用者の保存操作は「既存ドキュメントの更新」となり、`allow update: if false`で拒否される。読み取りと削除も、保存された所有者が異なるため拒否され、本人では取り除けない。

### 確認結果

攻撃側のアカウントで`victim_{eventId}`に`userId: attacker`のドキュメントを作成する操作が、実際のRulesで許可された。対象アカウントが同じ場所へ通常の保存データを書き込む操作と、読み取り・削除はすべて拒否された。通常の本人の保存・削除が成功することも対照として確認した。

前提は、対象者のUIDとイベントIDを知り、対象パスがまだ存在しないことである。既に他人が保存しているドキュメントの上書きや、他人の保存一覧の読み取りを確認した結果ではない。

### 対応案

作成時に`savedEventId == request.auth.uid + '_' + request.resource.data.eventId`を確認する。既存データにIDと所有者の不一致があれば、ルール修正だけでは解消しないため、該当データの確認と整理も別途必要になる。

## 2. P2：学生が企画したイベントの活動報告を公開できない

参照：

- [学生も開ける企画ダッシュボード](/Users/okk/my-project/aizu-connect/src/App.tsx:1402)
- [活動報告の入力・公開画面](/Users/okk/my-project/aizu-connect/src/screens/organization/OrganizationDashboard.tsx:1369)
- [活動報告の書き込みルール](/Users/okk/my-project/aizu-connect/firestore.rules:918)
- [活動報告画像の書き込みルール](/Users/okk/my-project/aizu-connect/storage.rules:95)

イベント作成と企画ダッシュボードは学生にも対応しており、自分のイベントを選ぶと活動報告の入力欄と公開ボタンが表示される。しかし、Firestoreの報告保存とStorageの報告画像アップロードは、両方とも団体アカウントだけを許可している。

### 確認結果

実際の`saveEventPlan`で学生・団体それぞれのイベントを作成し、承認済みで開催が終了した状態をテストデータとして設定した。その後、学生による自分の活動報告保存と報告画像アップロードは、ともに実際のRulesに拒否された。同じ条件で、団体による自分の報告保存と画像アップロードは成功した。

学生には画面があるのに、公開まで完了できない機能上の不整合である。公開処理にはエラー通知の`catch`もなく、`finally`だけのため、この権限拒否は画面上の説明にもつながらない。

### 対応案

学生主催者にも活動報告を提供するなら、イベント所有者の確認を維持しながら、FirestoreとStorageの両方を学生主催者に対応させる。団体限定の機能という仕様なら、学生には入力・公開画面を表示しない。いずれの場合も、公開処理の失敗を利用者へ通知する。

## 3. P3：公開停止後も、主催者の公開イベント件数が古いまま残る

参照：

- [公開時にだけ公開件数を再集計する処理](/Users/okk/my-project/aizu-connect/functions/src/triggers/notifications.ts:290)
- [公開停止・中止時の処理](/Users/okk/my-project/aizu-connect/functions/src/triggers/notifications.ts:328)
- [利用者向けの公開イベント件数表示](/Users/okk/my-project/aizu-connect/src/screens/shared/EventDrawer.tsx:393)

`publicOrganizerProfiles.publishedEventCount`は、イベントが公開された際に再集計する。一方、公開停止では同じ集計を更新する処理がない。利用者向け画面はこの保存値をそのまま「公開イベント○件」と表示するため、実際の公開件数と食い違う。

### 確認結果

同じ主催者の公開イベントが2件ある状態で公開トリガーを処理し、保存件数が2となることを確認した。その後、実際の管理APIで1件を公開停止し、公開停止トリガーまで処理した。実際の公開イベントは1件になったが、プロフィールの保存件数は2のまま残った。もう1件の公開イベントがあるため、その詳細画面でも古い件数が表示され得る。

### 対応案

公開状態へ入る・公開状態から出る・公開イベントを削除する経路で集計を更新する。重複実行や順序の違いで件数が壊れないようにし、必要なら再集計で修復できる構成にする。これは表示情報の整合性の問題であり、今回の範囲では申請権限や参加定員への影響は確認していない。
