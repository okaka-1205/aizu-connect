## 1. P1：削除処理中の申請が清掃から漏れ、個人情報と参加人数が残る

参照：

- [イベントの関連データ清掃と最後の本体削除](/Users/okk/my-project/aizu-connect/functions/src/callables/adminManageResource.ts:265)
- [ユーザーの関連データ清掃と最後の本体削除](/Users/okk/my-project/aizu-connect/functions/src/callables/adminManageResource.ts:407)
- [申請時のユーザー・イベント確認](/Users/okk/my-project/aizu-connect/functions/src/index.ts:312)
- [申請の読み取り権限](/Users/okk/my-project/aizu-connect/firestore.rules:513)

削除開始時に、ユーザーやイベントを「削除中」にする処理がない。関連データを順に清掃した後も、Storageの削除などが終わるまで、ユーザーは`active`、イベントは`published`のまま残る。この間、正規の`submitApplication`が新しい申請とチャット参加情報を作れる。既に終わった清掃は再実行されず、管理操作は削除完了となる。

### 再現結果

| 操作 | 削除完了後の状態 |
| --- | --- |
| イベントの関連データ清掃後、本体削除前に学生が申請 | イベント本体は消えたが、申請とチャット参加情報が残った |
| ユーザーの関連データ清掃後、Auth・本体削除前に本人が別イベントへ申請 | ユーザー本体は消えたが、氏名・参加者メッセージを含む申請とチャット参加情報が残り、イベントの参加人数も1のまま残った |

両方のケースで、元の主催者が残った申請を実際のRules経由で読み取れることも確認した。第三者が誰でも読めるという問題ではなく、削除対象のデータが削除完了後も主催者に提供され続ける問題である。

### 対応案

清掃開始前に、永続的な削除状態を保存し、新しい関連書き込みを止める。申請・企画保存・チャットなどの入口でその状態を検証し、検証と書き込みの競合も防ぐ。例えば企画保存は、現在ユーザーをトランザクションの外で確認しているため、削除状態の追加だけでなく、トランザクション内での再確認も必要になる。清掃は途中失敗から再試行できる形を維持する。

前回修正した「同じ申請を削除の再試行で二重に減算する問題」とは別の経路である。

## 2. P2：遅れたトリガーが、削除済みユーザーのデータを作り直す

参照：[申請更新トリガーの通知・活動実績作成](/Users/okk/my-project/aizu-connect/functions/src/triggers/notifications.ts:65)。

`notifyApplicationUpdated`は、イベントに含まれる過去の`before`・`after`だけから通知と活動実績を作る。申請やユーザーが現在も存在するか、削除中でないかを確認しない。

### 再現結果

1. 申請を`confirmed`から`attended`へ更新し、その更新イベントを保存した。
2. 管理者の通常のユーザー削除を完了させた。ユーザー・申請・活動実績が存在しないことを確認した。
3. 保存した更新イベントで、実際のトリガーを遅れて実行した。
4. 削除済みユーザーIDに紐づく`verified`の活動実績と通知が再作成された。

この問題には、削除中の本人による新しい操作は必要ない。Firestoreトリガーの呼び出し順序は保証されず、同じイベントが複数回配送される可能性もあるため、過去イベントの遅延・再試行を扱う必要がある。[Firebase公式資料](https://firebase.google.com/docs/functions/firestore-events#limitations)

### 対応案

トリガーの副作用を書き込む際に、現在の申請・ユーザー・イベントと削除状態を確認する。確認直後の削除との競合を残さないよう、可能な書き込みは確認と同じトランザクションに含める。削除完了後も参照できる削除記録を用意し、古いイベントからの再作成を止める。関連する通知・チャット作成トリガーにも同じ観点を適用する。

実際に再現したのは、申請更新からの通知と活動実績の再作成である。他の全トリガーを同じ条件で再現したという意味ではない。

## 3. P2：CSVに参加者の入力が数式のまま出力される

参照：

- [CSVのエスケープ処理](/Users/okk/my-project/aizu-connect/src/lib/eventUtils.ts:23)
- [参加者メッセージなどのCSV出力](/Users/okk/my-project/aizu-connect/src/screens/organization/organizationDashboardLogic.ts:97)
- [申請メッセージの受け取り](/Users/okk/my-project/aizu-connect/functions/src/index.ts:229)

現在の`csvEscape`は、ダブルクォートを重ねてセル全体を引用する処理だけで、数式の開始文字を無害化していない。参加者メッセージ・氏名・配慮事項など、学生が入力する値が出力される。

### 再現結果

正規の申請処理に参加者メッセージ`=1+1`を渡し、保存された申請を実際のCSV出力関数に渡すと、該当セルは`"=1+1"`となった。引用符で囲むだけでは、表計算ソフトでの数式解釈を防げない。悪用時の影響は、開くソフト・その設定・数式の種類・利用者操作に依存する。[OWASPのCSV Injection解説](https://owasp.org/www-community/attacks/CSV_Injection)

今回は数式が無害化されずCSVへ到達することまでを確認した。Excelなどでの実行、外部通信、情報の持ち出しは試していない。

### 対応案

CSVを開く対象ソフトを決め、数式として解釈される先頭文字・制御文字を扱う共通処理を追加する。保存後の再オープンも含めて対象ソフトで検証する。ソフトをまたぐ確実な文字列指定が必要なら、セルを文字列型として保存できる形式も選択肢になる。CSVには全ソフト・全用途に共通する万能な対策がないため、単に引用符を増やす修正では足りない。

### 対応案
