# Aizu Connect 1000ユーザー動線予測・テストレポート

調査日: 2026-08-01

対象: ローカルFirebase Emulator環境 / 現在の`main`作業ツリー

結論: 初回調査で優先度1〜3とした「通知漏れ」「検索漏れ」「審査漏れ」は、全件へ到達できるページングと追加読み込みUIを実装し、Emulator上で解消した。1000同時接続への耐性は今回の結果だけでは保証せず、別途負荷試験を行う。

## 1. 1000人の構成と予測動線

実アクセス解析がまだないため、以下を運用計画用の仮説とした。人数はユニークユーザー、各ステップは同じ人が複数回通る。

| ロール | 想定人数 | 主動線 | 想定ボリューム |
| --- | ---: | --- | ---: |
| 学生 | 900 | 登録/ログイン → ホーム → 検索/絞り込み → 詳細 → 保存/申請 → 主催者連絡 → 当日受付 → 活動実績 | 検索630〜720人、詳細270〜360人、申請90〜180人、連絡60〜140人、受付/実績40〜120人 |
| 主催者・団体 | 90 | 登録 → メール確認/管理者承認 → 企画作成 → 審査 → 公開 → 参加者承認/連絡 → 出欠/CSV | 企画作成40〜60団体、参加者管理20〜40団体 |
| 管理者 | 10 | ログイン → アカウント審査 → イベント審査 → 通報/退会対応 → 監査履歴 | 日常利用は少人数だが、停止時は全ユーザーへ波及 |

想定される最多動線は「学生の検索」、ピークが集中しやすい動線は「イベント公開直後の詳細閲覧・参加申請」、最も運用上のボトルネックになりやすい動線は「管理者審査」とした。

- 参加申請
- 学生による企画作成・審査申請
- プロフィール画像編集
- 個別/全体チャットと過去履歴
- 満員時のキャンセル待ち
- キャンセルによる繰り上げ
- 当日受付
- プロフィール、通知設定、保存、通報、活動証明
- 主催者ダッシュボード、参加者、メッセージ

- 承認待ち学生

- 学生検索で24件より後のイベントを追加表示

改善後の並列実行結果は **54/54成功（44.6秒）**。追加した検索ページングと管理キューページングは、3画面幅のすべてで横方向のはみ出しがなく、2ページ目の対象データまで到達できた。

- Functionsのロジック: **18/18成功**

### 手動確認

登録画面、学生ホーム、検索/絞り込み、満員表示、活動、チャット、管理者キューを実画面で確認した。追加読み込み欄は現在の読込件数と次の操作を一つのカードにまとめ、モバイルではボタンを全幅にして押しやすさを確保した。管理指標は未読込データがある場合に`50+`と表示し、固定上限を総件数と誤認しないようにした。

## 3. 優先度1〜3の解決結果

### 1. 通知の固定上限を解消

- イベント公開通知は有効学生を200人ずつ全件ページングする。
- 開催リマインダーは対象イベントを100件ずつ、各イベントの確定参加者を200人ずつ処理する。
- 中止・非公開通知は申請を150件ずつ全件処理する。
- 通知IDを決定的に生成し、再実行時の二重通知を防ぐ。
- Functionsの実行上限を処理量に合わせて540秒・512MiBへ調整した。

### 2. 学生検索の50件上限を解消

- 開催日時順のFirestoreカーソルページングへ変更し、24件単位で追加取得する。
- 「読み込み済み件数」「条件に合う表示件数」「残りの有無」を分けて表示する。
- PCでは横並び、モバイルでは全幅ボタンとなる追加読み込みカードを追加した。

### 3. 管理者審査キューの固定上限を解消

- イベント審査、アカウント審査、退会申請、通報へ50件単位の追加読み込みを追加した。
- 未読込データがある指標は`50+`のように表示し、最古日数も「読込範囲の最古」と明記する。
- 各キュー末尾に読込件数と「さらに50件」または「全件表示」を統一デザインで表示する。

## 4. 残る問題点と改善案

### 解決済み: 1000人へ通知が行き渡らない

**観測**

- イベント公開時に対象学生を最大498人しか取得しない（`functions/src/index.ts:1436`）。900学生の仮説では、設定条件以前に最大402人が評価対象外になる。
- 開催リマインダーは24時間以内のイベント100件、1イベントの確定者500人まで（`functions/src/index.ts:1655`）。定員は1000人まで許容されるため、最大500人がリマインダー対象外になり得る。
- イベント中止処理も申請1000件までで、定員外のキャンセル待ちを含めると残存データが出る可能性がある（`functions/src/index.ts:1523`）。

**実施済み**

- `startAfter`を使った全件ページングと小分け処理へ変更した。
- 1000人テストで5ページ目までの通知作成を確認した。
- 配送集計・再試行キューと1000人以上の本番相当負荷試験は次段階で実施する。

### 解決済み: 51件目以降のイベントが学生検索に出ない

**観測**

- 学生画面は開催が近い公開イベント50件だけを読み込む（`src/App.tsx:1061`）。「人気順」「新着順」もその50件内の並べ替えで、全イベントに対する並び順ではない。
- 90主催者が1件ずつ公開すると、開催日時によっては40件が検索不能になる。画面上には「さらに読み込む」がない。

**実施済み**

- 開催日時順のカーソルページングと24件単位の「次の24件を見る」を実装した。
- 読込件数と絞り込み後の表示件数を分け、検索可能範囲を誤認させない表示へ変更した。
- 全イベントに対する人気順・新着順のサーバー側並べ替えは、必要な複合インデックス設計と合わせて今後拡張する。

### 解決済み: 管理者の古い審査案件が見えなくなる

**観測**

- アカウント審査は新しい100件、イベント審査と通報は新しい50件だけ（`src/App.tsx:7815`、`src/App.tsx:7869`）。審査キュー側にはページングがない。
- 100件を超えると古い未処理案件が画面から消え、「最古の待ち日数」も実際より短く表示される。

**実施済み**

- 4種類の未処理キューへ追加読み込みを実装し、固定上限の外にある案件へ到達可能にした。
- 読込範囲と未読込の有無が分かる件数表示へ変更した。
- 厳密な総件数集計、全体の最古時刻、SLA・担当者管理は今後の運用機能として残る。

### P1: キャンセル待ち501人目以降の順位が重複する

**観測**

- 申請時の待ち人数を500件までしか数えないため、501人目以降は同じ順位になり得る（`functions/src/index.ts:1010`）。
- 繰り上げ候補は`createdAt`順でクエリせず、先に任意の100件を取得してからローカルで並べ替えるため、全体の先着順を保証しない（`functions/src/index.ts:1333`）。

**改善**

- イベント単位の連番をトランザクションで発行し、待ち順を不変キーとして保存する。
- 繰り上げは`orderBy("waitlistSequence", "asc").limit(1)`で取得する。
- 1000件の同時申請、取消、重複送信を対象にした競合テストを追加する。

### P1: 大規模イベントの全体チャットがホットスポットになる

**観測**

- 参加申請ごとに同じイベントルーム文書の`participantIds`配列へ追加する（`functions/src/index.ts:1068`）。同時申請が同一文書へ集中する。
- 全体チャット1投稿ごとに参加者全員の通知設定を読み、対象者分の通知を書き込む。1000人イベントでは、概ね999人分の読み書きが1投稿から発生し得る。
- Functions全体の`maxInstances`は10（`functions/src/index.ts:35`）。今回、1000人チャットの実負荷試験は未実施。

**改善**

- メンバーをサブコレクション化し、単一文書の巨大配列と同時更新を避ける。
- 通知をキューへ分離してチャンク処理し、レート制限と再試行を持たせる。
- 全体チャットは重要告知と会話を分離し、通知対象を抑えられる設計も検討する。

### P2: 固定上限により個人・主催者の履歴が消える

**観測**

- 学生の申請、チャット、保存、活動実績は各100件まで。通知は30件までで`orderBy`がなく、30件超では最新30件を保証しない（`src/App.tsx:1039`〜`1166`）。
- 主催者のイベントは50件、チャットは100件まで（`src/App.tsx:6012`〜`6105`）。
- 1イベントの参加者は最大1000件をリアルタイム購読し、画面へ一括描画する。最大規模では端末負荷とFirestore readコストが大きい。

**改善**

- すべての履歴一覧に`orderBy`とカーソルページングを付ける。
- 主催者の参加者一覧はサーバー側検索、ページング、行仮想化を採用する。
- 学生ログイン時に申請を`getDocs`と`onSnapshot`で二重取得しているため、一方へ統合する。各上限までデータがある場合、初期表示だけで約680文書以上を読む設計なので、1000人の一斉再訪では約68万read規模になり得る。

### P2: E2Eテストが端末間で状態を共有し、並列実行で不安定

**観測**

- Desktop/Mobile/Tabletが同じ`student-e2e`と同じチャット設定を変更する（`e2e/emulator-flows.spec.ts:232`）。
- 初回並列実行で通知ミュート状態が競合し1件失敗。再シードなしの再試行では、先行テストが作った申請によって別の曖昧一致が発生した。

**改善**

- プロジェクト別に学生、イベント、チャットルーム、申請IDを完全分離する。
- 各テストを作成データの後始末またはテスト単位のEmulator名前空間で隔離する。
- 状態テキストの検証は対象カードへスコープし、ページ全体の曖昧な一致を避ける。

### P3: 初回登録の離脱リスク

**観測**

- 学生の新規登録でメール、パスワード、表示名、学科、学年、興味、現在の活動、やりたいこと、規約同意を一度に提示する。
- CTAは「登録して始める」だが、メール確認や管理者承認が必要な利用者はすぐには始められない。

**改善**

- 最初はメール、パスワード、表示名、規約同意に絞り、学科・興味等は初回ログイン後の段階的プロフィールにする。
- アカウント種別とメールドメインに応じて、登録前に「メール確認のみ」「運営確認あり」と所要時間を表示する。
- 登録開始、登録完了、メール確認、検索開始、詳細、申請完了を計測し、実データで本レポートの仮説を更新する。

## 5. 良かった点

- 学生、主催者、管理者の役割ごとの主要機能が一つのE2E群でつながっている。
- 満員時に申請を拒否せずキャンセル待ちへ誘導し、取消時の繰り上げも実装済み。
- 個別チャット、全体チャット、通知ミュート、添付、既読、通報まで連絡動線が揃っている。
- 出席確認から活動証明へつながり、サービスの価値が参加後まで完結している。
- 3画面幅で主要画面の横スクロール有無を検証しており、クリーンデータでスマホ主要動線は通過した。

## 6. 次の推奨実施順

1. 待ち順を連番化し、1000件競合テストを作る。
2. 全体チャットのメンバー構造と通知ファンアウトを分割する。
3. 通知ジョブへ配送集計・再試行キュー・運営監視を追加する。
4. E2Eデータを画面幅ごとに完全分離し、状態変更テストの競合を防ぐ。
5. 1000仮想ユーザーの負荷試験を、閲覧70%、詳細20%、申請7%、チャット3%など実測に近い比率で実施する。

## 7. 今回保証できる範囲

保証できるのは、Emulator上で主要機能の単体動線が成立し、3画面幅の54ケースが通り、通知対象が1ページを超えても処理されること。Firebase本番環境のネットワーク遅延、課金、Functionsコールドスタート、1000同時接続、同一イベントへの1000同時申請、1000人チャット通知は未測定であり、別途負荷試験が必要。
